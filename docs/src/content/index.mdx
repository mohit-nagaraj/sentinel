# Sentinel

Sentinel connects product documentation, observed browser behavior, and source
implementation into evidence-backed application knowledge.

## Onboarding control plane

The control plane lists connected applications and collects four groups of
configuration through the web UI:

1. Application, immutable repository ref, documentation sources, optional
   GitHub installation identifier, and preview URL pattern.
2. Public, generic credential-field, or encrypted Playwright storage-state
   authentication.
3. Allowed hosts, action/screen/time budgets, target-owned setup/reset
   references, capability hints, and fixed high-risk action denials.
4. Compatibility evidence, warnings, blockers, human actions, proposed scope,
   and explicit confirmation.

The four fixed denials cover destructive operations, real payments, external
messages, and privilege changes. Non-destructive form submission is an explicit
setting.

## Compatibility

Inspection resolves a GitHub branch or commit to an immutable SHA and reads a
bounded, disposable checkout. The report cites evidence for TypeScript/React,
PHP/Laravel, Laravel routes, OpenAPI/Scramble, and Playwright assets, then names
the selected adapters. Web documentation and application probes enforce HTTPS,
DNS/public-network, approved-origin/path, redirect, timeout, and response-size
boundaries. Repository approval is checked before checkout. A real Playwright page
load pins the approved DNS result and applies the origin policy to HTTP and
WebSocket traffic.

Reports are `supported`, `partial`, or `blocked`. Missing optional target-owned
Playwright assets produce a warning; unreachable, unsafe, unsupported, or
misaligned core inputs produce blockers and operator actions.

## Secrets and authorization

The Proxy requires `SENTINEL_OPERATOR_TOKEN` through HTTP Basic or Bearer
authentication, and Server Actions repeat that request check on every call. The
server derives the owner UUID from `SENTINEL_OPERATOR_ID`, and storage queries
repeat the owner predicate next to the data. The client receives explicit public
projections, not database rows.

Credentials and storage state are transient form inputs. Supabase Vault stores
their encrypted values while ordinary tables retain opaque references only.
Client props, Server Action responses, logs, run state, source rows, graph data,
and model context do not contain plaintext values.

Credential and storage-state methods also require an operator attestation that
the deployment accepts automated login without CAPTCHA or mandatory human
verification. Missing attestation is a compatibility blocker with a human action.

## Freshness and confirmation

The stored input fingerprint excludes display-name changes and includes source,
deployment, documentation, authentication, preview, setup, and safety inputs.
Relevant edits invalidate prior inspection and confirmation. Applications with
published knowledge remain visibly stale after reinspection until a later
refresh succeeds.

Scope confirmation reconstructs and fingerprints the submitted non-secret form,
rejects secret/authentication edits, and then uses a compare-and-set write against
the current inspected fingerprint. Editing an inspected field requires
reinspection. The confirmed application is ready for initialization, but
onboarding itself creates no initialization run.

## GitHub pull-request trigger

The configured GitHub App subscribes only to pull-request events and holds
Contents read, Pull requests read, and Checks write permission. Sentinel accepts
opened, reopened, synchronize, and ready-for-review actions for non-draft pull
requests. It does not write repository contents, PR text, issues, branches, or
comments.

The webhook route authenticates the exact request bytes before parsing, then
confirms the delivery head against current GitHub PR metadata. A single PostgreSQL
transaction deduplicates the delivery, creates or reuses the immutable-head
assessment, and enqueues the worker-owned assessment run. When a newer head
arrives, the prior run is cancelled and the prior assessment becomes non-current.
Delayed older heads and replays remain non-current.

Each assessment/head owns one concise GitHub check linked to the canonical
Sentinel assessment URL. Check creation uses a durable lease and recovers partial
external writes through the assessment ID stored as GitHub `external_id`.
Running and terminal publication recovers a missing initial check, then requires
the same assessment and head to remain current. Predicted risk is not a test
failure: risk, unknown scope, and unavailable verification remain neutral, while
deterministic verification failure and infrastructure analysis failure are
distinguished explicitly.

The authenticated manual PR URL route resolves the current GitHub metadata and
invokes the same assessment service and execution budget as the webhook route.

## Specialist orchestration

Documentation, Code, and Application specialists share one durable mission
lifecycle. Each composition fixes its agent identity, mission modes, prompt,
model, described tools, completion validator, and runtime limits. That
configuration is fingerprinted in checkpoint state, so recovery cannot switch an
in-flight mission to different authority.

Models choose only from the current specialist's strict tool schemas. The runtime
checks agent and mode permission, mission allowlists, scope, call correlation,
replay identity, and budget reservation before execution. Rich source and browser
records stay behind injected durable stores; checkpoints retain bounded hashes,
evidence references, usage, progress, human decisions, and terminal results.

Code missions navigate prepared source and endpoint indexes and accept proposed
relationships only when observed structural evidence supports them. Application
missions select opaque browser actions, retain policy authority in the browser
runtime, bind recovery to the same authentication reference, and require observed
transitions to address mission questions and success criteria.

State changes commit before their lifecycle events. Event idempotency keys make
decision, tool, evidence, budget, interrupt, and terminal history retry-safe.
Mission continuation and authorized human resume remain on the same lease-guarded
checkpoint thread without repeating completed tool effects.

## Realtime specialist activity

The authenticated `/runs` workspace reconstructs ordered Postgres events into
Documentation, Code, and Application lanes with a separate Curator reconciliation
feed. It shows bounded decision summaries, reason codes, tool and browser action
status, query-free request routes, evidence gains, budgets, interrupts, and typed
terminal states. React renders all persisted text inertly; prompts, hidden
reasoning, selectors, arbitrary DOM, credentials, and unbounded provider details
are outside the event projection.

Each inserted event sends only its run UUID and sequence to a private Supabase
Broadcast topic. A four-minute owner JWT authorizes the topic through
`realtime.messages` RLS, while the client fetches canonical pages after its last
durable cursor. Serialized catch-up rejects gaps and conflicting duplicates, so
reload and reconnect produce the same visible order.

Application screenshots remain in private Storage. The server verifies the
owned application, run, screenshot type, and PNG/JPEG MIME before returning a URL
that expires in at most five minutes. Pause waits for a worker safe boundary;
stop, retry, and one-time interrupt responses reuse the durable run-control API.
